# Evidence-based promotion (Phase17 Step6)

Opt-in `budgeted_paired_probe` v2 retains this graph and adds bounded paired
screening inside the authorized training dependency, without a hard V gate.
See [adaptive-paired-early-stop.md](adaptive-paired-early-stop.md) for budgets,
simultaneous intervals, group isolation and recovery. The metric-policy text
below describes legacy `metric_gate` behavior.

One existing LangGraph and the same five Agents:

AuditRequest → profile / visual discovery → Identify → pre-validation candidate
screening → capabilities → Executive → feasibility → validation-stage sidecar
→ Stage-1 Quantitative ∥ Qualitative → evidence promotion → Stage-2 validation
→ existing EvidenceCalibration → Summarize → deterministic audit report.

Candidate screening remains a pre-validation triage. Evidence promotion uses
only finalized Stage-1 measurements, candidate identities and finalized
qualitative coverage. Neither controller confirms or disproves a shortcut.
Scientific assessment still comes from the original EvidenceLedger/SummaryReport.

## Classification and execution

The Python registry in `experiment/evidence_promotion.py` classifies actual
existing backend contracts. `statistical_check` uses bounded metadata association
and bootstrap statistics; `subgroup_evaluation` computes statistics from
authorized, already available prediction rows; `metric_computation` computes
bounded row metrics. None trains or invokes a task model. These are cheap.
Original row/iteration bounds remain in force; cheap does not mean free.

`model_evaluation` runs a predictive probe (including fitting), so it is expensive
even though its name could suggest mere metric computation. Training, task-model
evaluation, OOD, intervention, ablation and counterfactual backends are expensive.
Steps depending on expensive work also inherit the expensive tier.

Known bounded qualitative checks use the existing sample/descriptor backend and
inspection limits. Unclassified qualitative checks conservatively go to Stage-2.
Classification is versioned `backend-cost-v1` and is never generated by an LLM.

The sidecar preserves original AnalysisTask and PlanStep IDs. Stage-1 filters
every compiled/refreshed quantitative plan before mandatory execution and the
Provider loop. Its task runtime independently rejects expensive ToolCalls.
Stage-2 verifies the persisted promoted decision before executing a task, then
restores its exact Stage-1 ToolResults. Missing provenance fails closed instead
of running cheap steps again. Original ToolCall finalization, permissions, task
isolation, timeout/retry and shared budgets remain the execution boundary.

## Frozen policy

`PromotionPolicy` contains version/calibration status, applicable evidence types,
explicit metric rules (`experiment_type`, metric, comparator, threshold), minimum
sample count, quantitative combination rule, qualitative rule and missing-evidence
behavior. Policy and result hashes use canonical sorted JSON / SHA-256.

**Default: `unconfigured-v1`, no numeric thresholds.** It collects Stage-1 evidence
and returns `deferred_insufficient_evidence`; expensive validation is skipped.
There is no invented calibrated policy and no implicit legacy threshold. Before
paper experiments the experiment owner must separately determine and freeze a
formal policy. An internally supplied policy can be placed in RunRequest metadata
as `promotion_policy`; dataset-only users do not need task/experiment JSON.

For an explicitly configured policy, any covered rule satisfied promotes. A low
signal termination requires usable evidence covering every configured rule with
none satisfied. Missing metrics, failed/inconclusive execution, absent policy, or
insufficient samples defer. These are resource-routing decisions, not statistical
confirmation or proof of absence. The configured comparisons are copied literally;
the controller does not choose their numerical cutoffs or scientific calibration.

Current finalized qualitative results lack a validated automatic strength rule.
`qualitative_promotion_unavailable` is recorded. An LLM's assessment/confidence,
raw reasoning, or a `strong=true` statement cannot drive promotion.

## Persistence and recovery

- `validation/stage_plan.json`: frozen classification, original step IDs, full input
  hash, policy and policy hash.
- `validation/stage1/<task>-<branch>.json`: hashed finalized Stage-1 cache, separate
  from the later final result for the same task.
- `promotion/policy.json`: exact frozen policy.
- `promotion/result.json`: policy version/hash, Stage-1 projection hash, result hash
  and per-candidate decision/reasons/measurement references.

The gate cache must match the same policy and source projection. It is reused on
resume without a Provider, experiment or new decision. Stage-1 caches also cover
recovery after finalization but before a graph checkpoint. Stage-2 cannot consume
future model results as promotion inputs. Hidden/evaluator truth is not read or
hashed; only an exact public numeric metric projection is admitted.

Promoted does not grant extra budget. Existing exhaustion produces the existing
failed execution status and preserved trace, not an unbudgeted experiment.

## Reports and progress

Audit JSON separately stores `screening` and `evidence_promotion` (the latter also
contains frozen policy/sidecar, Stage-1 results and Stage-2 execution trace). Formal
findings are copied unchanged. Skipped expensive work contributes a recorded
controller limitation to finalized task results, which the existing synthesis can
see. Old completed runs without promotion authority export it as unavailable.

The existing monitor adds Stage-1 Validation, Evidence Promotion and Stage-2
Validation rows and per-candidate decisions. Generated/pre-screen-promoted,
evidence-promoted, terminated and deferred counts are shown separately. No saved
dollars, GPU hours or counterfactual token savings are estimated.
